## 8.1 소개

템플릿의 기능

- 정보 손실 없이 타입을 인수로 전달할 수 있음 + 표현이 매우 유연해짐
- 구체화 타임에 다양한 컨텍스트 정보를 결합할 수 있음: 최적화에 유리

## 8.2 Concept

concept: 템플릿 인수가 만족해야하는 요구 사항

### 8.2.1 콘셉트의 용법

```cpp
template<typename Seq, typename Value>
Value sum(Seq& s, Value v)
{
	for (const auto& x : s)
		v+=x;
	return v;
}
```

- `Seq`는 for문으로 돌 수 있는 것이어야 하고 (순회 가능한 시퀀스)
- `Value`는 `+=`가 되는 숫자 같은 것이어야 함

그런데 typename으로는 표현할 수 없으므로

```cpp
template<Sequence Seq, Number Num>
Num sum(Seq& s, Num v) { ... }
```

이렇게 바꿔서 표현하는데, 이때 `Sequence`, `Number`가 콘셉트

```cpp
template<typename Seq, typename Num>
	requires Sequence<Seq> && Number<Num> && Arithmetic<range_value_t<Seq>,Num>
Num sum(Seq& s, Num n);
```

이렇게 써도 의미는 같다.

### 8.2.2 콘셉트 기반 오버로딩

타입에 따라 다른 버전을 자동으로 고르기

```cpp
template<forward_iterator Iter>
void advance(Iter p, int n) { while (n--) ++p; }        // 한 칸씩 밖에 못 가는 애용 (느림)

template<random_access_iterator Iter>
void advance(Iter p, int n) { p += n; }                   // 한번에 점프 가능한 애용 (빠름)
```

`list`의 반복자는 한 칸씩만 갈 수 있고, `vector`의 반복자는 원하는 만큼 점프할 수 있다.

|  | `vector` | `list` |
| --- | --- | --- |
| 메모리 구조 | 연속된 공간에 원소를 나란히 저장 | 원소들이 메모리 여기저기 흩어져 저장 |
| n칸 이동 | 주소 계산 한 번 (`p += n`) | 포인터를 n번 따라가야 함 |
| 만족 콘셉트 | `random_access_iterator` | `forward_iterator` |

`advance(vector반복자, 10)`이라고 부르면 컴파일러가 random_access_iterator 조건을 만족하는지 확인하고 알아서 빠른 버전을 골라준다. `list`로 부르면 자동으로 느린 버전이 선택된다.

→ 런타임에 if문으로 검사하는 게 아니라 컴파일 시점에 이미 결정되어 속도 손해가 없다.

### 8.2.3 유효한 코드

Sequence, Number라는 조건을 컴퓨터가 판단하는 방법: 그 타입으로 이 코드를 짜봤을 때 컴파일이 되는지 확인

```cpp
template<forward_iterator Iter>
    requires requires(Iter p, int i) { p[i]; p + i; }
void advance(Iter p, int n) { p += n; }
```

앞의 requires: 지금부터 조건을 걸겠다는 조건절

뒤의 requires(Iter p, int i): Iter 타입인 p 로 p[i]와 p+i라는 코드를 짜서 컴파일되는지 확인

```cpp
template<typename Seq>
    requires Sequence<Seq>
void f(Seq s);
```

정리: 콘셉트 조건이 참인지는 결국 '그 코드가 컴파일되는지'로 판단하고, 그걸 문법으로 쓴 게 `requires{...}` 표현식이다.

**주의**: 콘셉트로 뽑아내지 않고 코드에 `requires requires { ... }` 등으로 사용하며 콘셉트를 너무 저수준으로 사용하지 말 것. `random_access_iterator`처럼 이름 붙은 콘셉트를 갖다 쓰는 것을 권장

### 8.2.4 콘셉트 정의

```cpp
template<typename T>
concept Equality_comparable =
    requires (T a, T b) {
        { a == b } -> Boolean;
        { a != b } -> Boolean;
    };
```

`Equality_comparable`이라는 이름의 새 콘셉트를 만든다.

조건: T 타입인 a, b가 있을 때 `a==b`도 되고 `a!=b`도 되고, 그 결과가 Boolean이어야 한다.

```cpp
static_assert(Equality_comparable<int>);   // 성공 (int는 ==,!= 됨)

struct S { int a; };
static_assert(Equality_comparable<S>);     // 실패 (내가 만든 S는 ==,!=를 정의 안 했음)
```

```cpp
template<typename T>
concept Number =
    requires(T x, T y) {
        x+y; x-y; x*y; x/y;   // 사칙연산 가능한지 확인
    };
```

```cpp
template<Equality_comparable T>
bool cmp(T a, T b) { return a < b; }   // <는 조건에 없었는데 내부에서 씀

bool ok = cmp(2, 3);            // OK — int는 우연히 <도 되니까 통과됨
bool err = cmp(2+3i, 3+4i);     // 에러 — complex는 <가 없어서 실제 컴파일할 때 터짐
```

`Equality_comparable`이라고만 조건을 걸어놓고 내부에서 실수로 `<`를 써버리면, `int`처럼 우연히 `<`도 되는 타입으로는 잘 돌아가서 문제를 못 느끼다가, complex처럼 `<`가 없는 타입을 넣는 순간 뒤늦게 에러가 생긴다. 따라서 콘셉트를 만들 때는 함수가 실제로 쓰는 연산을 빠짐없이 조건에 넣어야 한다.

**주의**: 콘셉트는 함수를 부를 때 인수가 조건에 맞는지만 검사하고, 함수 내부 코드가 그 조건만으로 안전한지는 검사하지 않음

### 8.2.5 콘셉트와 auto

`auto` : 제일 느슨한 조건의 콘셉트

```cpp
auto twice(Arithmetic auto x) { return x + x; }   // 숫자류만 받음
auto thrice(auto x)          { return x + x + x; } // +가 되면 뭐든 받음

auto x1 = twice(7);      // OK
string s = "hi";
auto x2 = twice(s);      // 에러: string은 Arithmetic 아님
auto x3 = thrice(s);     // OK: string도 +가 되니까
```

콘셉트 + auto 조합으로 인자·반환값·변수의 타입을 원하는 만큼 좁힐 수 있다

---

### 8.2.6 콘셉트와 타입

type이 하는 역할

| 역할 | type | concept |
| --- | --- | --- |
| 어떤 연산이 가능한지 정함 (int는 +,-가 됨) | O | O |
| 함수 선언에 필요함 (매개변수 타입 명시) | O | O |
| 메모리에 어떻게 배치되는지 정함 (int는 4바이트) | O | X |
| 여러 타입을 하나의 집합으로 묶어서 다룸 | X | O |

콘셉트는 메모리 배치에는 관여하지 않는다. 대신 여러 타입을 하나로 묶은 집합을 다룰 수 있다. `int`는 딱 하나의 구체적인 타입이지만, `Number`는 int든 double이든 Matrix든 숫자처럼 동작하는 모든 타입을 한 번에 가리킨다.

콘셉트를 사용하면 다양한 타입에 다 쓸 수 있는 유연한 함수가 되기 때문에 **함수 인자는 구체 타입보다 콘셉트로 제약하는 게 이상적임**

## 8.3 제네릭 프로그래밍

그 조건을 가지고 실제로 좋은 제네릭 코드를 어떻게 만드는가

### 8.3.1 콘셉트의 용법

좋은 콘셉트는 지어내는 게 아니라 상식적인 개념을 발견해서 이름 붙이는 것

`regular` : `int`나 `vector`처럼 "평범하게, 상식적으로" 동작하는 타입

```cpp
// 나쁜 예 — 이름과 실제 의미가 안 맞음
concept Addable = requires(T a, T b) { a / b; };  // 이름은 "더할 수 있음"인데 실제론 나눗셈 검사
```

콘셉트를 만들 땐 상식적으로 알고 있는 개념을 잘 찾아서 이름 붙여야 한다. 그리고 이름과 실제 의미가 일치해야 한다

---

### 8.3.2 템플릿을 이용한 추상

처음부터 완벽하게 일반적인 코드를 짜려고 하지 마라. 구체적인 것부터 시작해서 단계적으로 일반화해라

1단계

```cpp
double sum(const vector<int>& v)
{
    double res = 0;
    for (auto x : v) res += x;
    return res;
}
```

vector<int>의 합을 double로 구한다

- 왜 꼭 `int`만 더해야 하지? `double`이나 다른 숫자는 안 되나?
- 왜 꼭 `vector`여야 하지? `list`는 안 되나?
- 왜 결과가 꼭 `double`이어야 하지?
- 왜 꼭 `0`에서 시작해야 하지?

2단계

```cpp
template<forward_iterator Iter, Arithmetic<iter_value_t<Iter>> Val>
Val accumulate(Iter first, Iter last, Val res)
{
    for (auto p = first; p!=last; ++p)
        res += *p;
    return res;
}
```

1. 구체적인 버전을 하나 작성한다
2. 그걸 디버깅하고 테스트하고 성능도 재본다
3. 마지막에 구체 타입을 템플릿 인자로 하나씩 바꿔서 일반화한다

## 8.4 가변 인자 템플릿

인자 개수도 타입도 정해지지 않은 함수, 보통 재귀로 구현한다.

`printf`처럼 인자가 몇 개 올지도 모르고, 각각 타입도 다 다를 수 있는 함수를 만들고 싶을 때 사용

```cpp
template<typename T>
concept Printable = requires(T t) { std::cout << t; };  // 출력 가능하기만 하면 OK

void print() { }   // 인자 없으면 아무것도 안 함 (재귀의 끝)

template<Printable T, Printable... Tail>
void print(T head, Tail... tail)
{
    cout << head << ' ';   // 맨 앞 하나 출력하고
    print(tail...);        // 나머지를 다시 print()에 넘김 (재귀)
}
```

호출 예: `print(1, 2.2, "hello")`

동작 원리

| 단계 | head | tail | 동작 |
| --- | --- | --- | --- |
| 1 | 1 | (2.2, "hello") | `1` 출력하고 `print(2.2, "hello")` 호출 |
| 2 | 2.2 | ("hello") | `2.2` 출력하고 `print("hello")` 호출 |
| 3 | "hello" | () | `hello` 출력하고 `print()` 호출 |
| 4 | - | - | 인자 없음 → 그냥 끝 |

---

### 8.4.1 폴드 표현식

인자 팩을 연산자로 쭉 이어붙이는 걸 재귀 없이 한 줄로 쓰는 것

```cpp
template<Number... T>
int sum(T... v)
{
    return (v + ... + 0);   // v에 있는 모든 값을 +로 이어붙이고 마지막에 0을 더함
}

int x = sum(1, 2, 3, 4, 5);   // 15
```

`(v + ... + 0)` : 오른쪽부터 괄호를 쳐가며 계산

```cpp
v[0] + (v[1] + (v[2] + (v[3] + (v[4] + 0))))
```

---

### 8.4.2 인수 포워딩

받은 인자를 복사 없이 그대로 다음 함수로 넘기는 것

```cpp
template<concepts::InputTransport Transport>
class InputChannel {
public:
    InputChannel(Transport::Args&&... transportArgs)
        : _transport(std::forward<TransportArgs>(transportArgs)...)
    {}
    Transport _transport;
};
```

`InputChannel`의 생성자가 받은 인자들을 복사하지 않고, 원래 형태 그대로 `Transport`의 생성자한테 넘겨줌

## 8.5 템플릿 컴파일 모델

콘셉트 있는 건 호출할 때 바로 검사, 없는 건 코드 찍어낼 때(구체화 시점) 늦게 검사됨 → 그래서 템플릿 정의는 꼭 헤더에 넣어야 함

1. **콘셉트로 제약된 인자**는 함수를 호출하는 시점에 바로 검사됨. 문제 있으면 그 자리에서 바로 에러가 남.
2. **콘셉트 없이 쓰인 템플릿 인자**는 템플릿을 실제 코드로 찍어내는 시점(instantiation)까지 미뤄짐
